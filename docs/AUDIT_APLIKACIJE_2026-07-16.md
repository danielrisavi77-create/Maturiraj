## 🔴 P0 — Riješiti odmah (3)

### 1. MAT simulator: '_META' audit object counted in the scoring denominator makes 100% impossible on every math exam
`components/discere/mat/MatFullSimulator.jsx:line 116 (qs: m.qs) — also components/simulator/MatEngineCore.tsx:5012 (const QSX=exam.qs) and scoring at 5228-5231/5336-5347` · bug · Sadržaj / točnost

- **Problem:** Every externalized math exam file ends its `qs` array with an audit-metadata object `{_META:true, auditedAt,...}` (verified: 69 of 70 exams carry `_META===true`, plus 4 more `_META` markers; content/simulator/mat/exams/2023_ljeto_A.mjs:1164). MatFullSimulator builds EXAMS with `qs: m.qs` WITHOUT filtering _META (line 116), unlike its sibling components/simulator/MatEngine.tsx:29 which does `qs:(qs\|\|[]).filter(q=>!q._META)`. The engine then sets `const QSX=exam.qs` (MatEngineCore.tsx:5012) with no filter. In finishExam, `autoQ2=QSX.filter(q=>q.type!=="proof"&&q.type!=="sa")` (5228) — the _META object has no `type`, so it passes the filter; `totalPoints2` adds `(q.points\|\|1)=1` for it (5229), but `chk(_META,...)` returns null (MatEngineCore.tsx:1028, no matching type) so it is never earned. The done-render path (5336-5347) has the identical flaw. /discere/matematika is served by MatFullSimulator (DiscereApp.jsx:18), and real exams pass `exam:EXAMS[examKey]` straight to Sim (MatEngineCore.tsx:10760-10763), so there is no mitigation.
- **Utjecaj:** pct=round(earnedPoints/totalPoints*100) can never reach 100 on any real exam — computed max is 94-96% (e.g. 2016_ljeto_A earnable 34/36 → 94%; single-_META exams cap ~94-96%). Every math score is deflated by ~1 point out of the auto total (more on short exams, some exams lose 2), `if(pct2===100) fireConfetti()` (5232) never fires, the 'Savršenstvo/perfect' achievement keyed on `h.pct===100` (2812) is permanently unreachable, the reported question `total` is off-by-one, topic_breakdown gains a phantom always-wrong 'ostalo' entry that skews coach weak-topic tips (5237-5246), and the deflated pct is persisted to Supabase sim_progress via flushAttempt→saveSimResult (MatFullSimulator.jsx:289-305), corrupting parent-dashboard analytics.
- **Popravak:** Filter _META where MatFullSimulator builds EXAMS: `qs: (m.qs \|\| []).filter(q => q && !q._META)` (MatFullSimulator.jsx:116), mirroring MatEngine.tsx:29. Additionally harden the engine at MatEngineCore.tsx:5012: `const QSX=(exam.qs\|\|[]).filter(q=>q&&!q._META);` so any unfiltered source (custom imports, virtual/practice pools) is also safe.

### 2. Compare share page uvijek redirecta na /prijemni — searchParams nije awaitan (Next 16)
`app/prijemni/compare/page.js:ComparePage, line 9-13` · bug · Frontend / UX

- **Problem:** Ovo je Server Component u Next.js 16 (package.json: next ^16.1.7). U Next 16 je sinkroni pristup request-time API-jima potpuno uklonjen — `searchParams` je Promise i MORA se awaitati (potvrđeno u službenoj v16 upgrade dokumentaciji; ostatak repozitorija to poštuje, npr. `await params` u app/api/exams/[razina]/route.js i app/api/parent/child-dashboard/[childId]/route.js). Ovdje se `searchParams.ids` čita direktno na Promise objektu → `.ids` je `undefined` → `undefined?.split(',') \|\| []` → `ids = []` → `ids.length < 2` je uvijek true → `redirect('/prijemni')` se izvršava UVIJEK.
- **Utjecaj:** Cijela /prijemni/compare stranica je mrtva: svaki podijeljeni link oblika /prijemni/compare?ids=... (koje generira handleCompareShare u app/prijemni/page.js, native share + clipboard + WhatsApp) redirecta natrag na /prijemni bez ijedne usporedbe. Viralna share-petlja usporedbe studija je potpuno slomljena, a korisnik koji klikne podijeljeni link nikad ne vidi obećani sadržaj.
- **Popravak:** Awaitaj searchParams: `export default async function ComparePage({ searchParams }) { const { ids: raw } = await searchParams; const ids = raw?.split(',').filter(Boolean) \|\| []; ... }`. (Isti async-access bug vjerojatno postoji i u app/kalkulator/page.js:6-7 gdje se searchParams sinkrono prosljeđuje u new URLSearchParams — provjeriti izvan ovog batcha.)

### 3. Zadana cijena na landingu (Starter 6,99€ godišnje) i cijeli 3mj/6mj model nemaju checkout — slijepa ulica
`components/landing/Cijene.jsx:BILLING_OPTIONS (lines 5-10), default billing "god" (line 68); app/api/checkout/route.js PLANOVI (lines 10-14); app/pro/page.js checkoutPlan (lines 13-16)` · integracija · Frontend / UX

- **Problem:** Cijene sekcija nudi 4 razdoblja naplate (mj/3mj/6mj/god) i po defaultu prikazuje "Godišnje", pa je prva cijena koju posjetitelj vidi Starter 6,99€/god (total 83,88€) te Pro 10,00€/god. No checkout (app/api/checkout/route.js:10-14) poznaje samo 3 cijene: starter (mj), pro (mj), pro_god (god). Ne postoje price ID-evi za 3mj, 6mj ni za Starter godišnje. Klik na 'Odaberi Pro'/'Počni s Starterom' ide preko onPlan (app/page.jsx:148-151) na /pro BEZ prijenosa odabranog razdoblja — /pro starta na 'monthly'. Ako korisnik na /pro prebaci na 'Godišnje' da dobije obećanih 6,99€, gumb Standard je onemogućen ('Godišnji Standard uskoro', app/pro/page.js:164, checkoutPlan.yearly=null).
- **Utjecaj:** Najistaknutija oglašena cijena (default god) i cijele 3mj/6mj ponude su nekupljive. Korisnik s najvišom kupovnom namjerom (odabrao godišnje/6mj) udara u onemogućen gumb ili nestalu ponudu — direktan gubitak konverzije i dojam bait-and-switcha (potrošački rizik u EU/HR).
- **Popravak:** Uskladi ponudu s checkoutom: ili (a) ukloni 3mj/6mj i Starter-god iz Cijene i /pro dok ne postoje Stripe cijene, ili (b) dodaj price ID-eve i mapiranja. Do tada postavi default billing na 'mj' (Cijene.jsx:68) i prenesi odabrano razdoblje kroz onPlan u /pro (npr. /pro?billing=god) da se prikaz podudara s klikom.
